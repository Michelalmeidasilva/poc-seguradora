# Deploy-Ready Implementation Plan (Plan 7)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the POC deployable on Google Cloud Run without touching the cloud from this repo: verified Docker images, a local `docker-compose` stack that runs the whole product end to end, Terraform for the three Cloud Run services (plus a fake-services service while the real `svc-*` do not exist), a GitHub Actions deploy workflow, a post-deploy smoke test and a runbook.

**Architecture:** `web` (nginx, public) proxies same-origin `/v1` to `gateway` (public Cloud Run URL, protected by Origin/cookie/rate limits); `gateway` calls `chatbot` and `chatbot` calls the services only over internal ingress through Direct VPC egress; the services are `fake-services` (a container of the contract-conformant fake already used by the chatbot tests) until the real `svc-*` exist. A node smoke script (`infra/smoke.mjs`) drives the public URL and runs against compose locally and against Cloud Run after deploy.

**Tech Stack:** Docker / docker-compose, nginx 1.27, Terraform ≥ 1.10 (`hashicorp/google`), GitHub Actions (Workload Identity Federation, no keys), Node 22 for the smoke script. No new runtime dependency in the apps.

**Spec:** `docs/superpowers/specs/2026-10-10-whatsapp-chatbot-poc-design.md` sections 6, 12, 13; `docs/superpowers/specs/2026-10-10-gateway-chatbot-contract.md`; deploy-related decisions already recorded in `apps/*/CHECKLIST.md` ("Pendências").

## Global Constraints

- **Nothing in this plan calls GCP.** No `terraform apply`, no `gcloud`, no image push. Terraform is verified with `terraform fmt -check` and `terraform init -backend=false && terraform validate`; workflows are verified with `actionlint` (run via `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:latest`) only. The user runs the first apply with their own account (runbook).
- No secrets or real project ids in the repo. `SESSION_SECRET` is generated by Terraform (`random_password`, 48 chars) and stored in Secret Manager; services read it through `secret_key_ref`. Terraform state holds it, so the runbook requires a private GCS state bucket.
- Cloud Run settings: `gateway` and `chatbot` `max_instance_count = 1` (their session/turn state is in memory; two instances would split sessions) and `session_affinity = true`; `web` `max_instance_count = 2`; request `timeout = 3600s` for `web` and `gateway` (SSE). CPU always allocated is NOT used (CPU only during requests) except `gateway` which holds SSE connections: `cpu_idle = false` for gateway only.
- Network: `chatbot` and `fake-services` use `ingress = INGRESS_TRAFFIC_INTERNAL_ONLY`; `gateway` and `chatbot` reach them through Direct VPC egress (`egress = ALL_TRAFFIC`) on a subnet with `private_ip_google_access = true`. Marked in the runbook as "validate on first apply with the post-deploy smoke test" because it cannot be exercised offline.
- Same-origin cookie: `web` and `gateway` URLs differ, but the browser only talks to `web` (nginx proxies `/v1`), so the session cookie is first-party. Gateway env: `ALLOWED_ORIGIN` = web public URL, `COOKIE_SECURE=true`, `COOKIE_SAME_SITE=lax`. URLs are computed without a Terraform cycle from `data.google_project.project.number`: `https://<service>-<project_number>.<region>.run.app`; an optional `web_custom_domain_url` variable overrides the web URL.
- `TRUST_PROXY_HOPS`: Terraform variable `trust_proxy_hops`, default `3` (client → Google front end → nginx on Cloud Run → Google front end → gateway). The runbook has a step to verify it from the gateway logs and says how to correct it. Do not hard-code it elsewhere.
- Budget protection (spec section 13): optional `google_billing_budget` with an alert when `billing_account_id` is set; otherwise skipped.
- Images are built from the repo root with the existing per-app Dockerfiles; do not ship test code in the gateway, chatbot or web images. `fake-services` has its own Dockerfile under `infra/fake-services/`.
- Tests/verification must run locally with Docker Desktop running (it is). Clean up containers/networks/volumes created by tests (`docker compose down -v`).
- Ownership: this plan edits `infra/**` (row `deploy`), `.github/workflows/**`, root `README`/docs for the runbook (`docs/deploy.md` is allowed), and, for the nginx/Dockerfile of the web, `apps/web/nginx.conf.template` and `apps/web/Dockerfile` (row `web-chat`, reopened). Gateway/chatbot Dockerfiles are not expected to change; if a task shows they must, STOP and report (the rows `gateway`/`chatbot` are `done`).
- Comments English, docs pt-BR, conventional commits, `CHECKLIST.md` honest.

## Review Focus

1. nginx resolves the gateway hostname only once at start; if the gateway's IP changes the proxy keeps using the stale IP and `/v1` fails until restart. After the fix, changing the upstream IP at runtime must keep working (test with compose: recreate the gateway container so its IP changes, without restarting nginx).
2. SSE through nginx: no buffering, long timeouts, and a reconnect with `Last-Event-ID` replays correctly through the proxy.
3. `Host` header sent to the gateway must be the gateway's own host (Cloud Run routes by Host); `Origin` must still reach the gateway unchanged (it enforces `ALLOWED_ORIGIN`).
4. Secret handling: no secret value in Terraform outputs, logs or the repo; `terraform validate` passes without any credentials.
5. A failed smoke step must name which hop failed (web, session, SSE, chatbot, services) rather than "timeout".
6. First-time operator experience: the runbook can be followed top to bottom by someone who has never used this repo (bootstrap state bucket, WIF, variables, apply, smoke, rollback, teardown).

### Task 2: nginx hardening for Cloud Run (dynamic upstream DNS, Host, SSE)

**Files:**
- Modify: `apps/web/nginx.conf.template`, `apps/web/Dockerfile` (only if needed), `apps/web/CHECKLIST.md`
- Create: `infra/test-nginx-dns.sh` (or `.mjs`) — the runtime IP-change test from Review Focus 1

**Interfaces:**
- nginx must resolve the gateway host at request time: use `resolver ${NAMESERVER} valid=10s ipv6=off;` plus `set $gateway "${GATEWAY_URL}"; proxy_pass $gateway;` (careful: with a variable `proxy_pass` the URI part is not auto-stripped/appended — verify `/v1/...` paths reach the gateway unchanged, including the query string, with `proxy_pass $gateway$request_uri;`). The nameserver is not known statically: derive it in the container at start from `/etc/resolv.conf` with a script in `/docker-entrypoint.d/` (nginx's entrypoint runs those scripts before the template envsubst; name it so it runs BEFORE `20-envsubst-on-templates.sh`, e.g. `15-resolver.sh`, and `export NAMESERVER`). On Cloud Run `/etc/resolv.conf` points at the metadata resolver; locally at Docker's `127.0.0.11`.
- `proxy_set_header Host` must be the gateway's host (derive from `GATEWAY_URL` with the same entrypoint script, export `GATEWAY_HOST`); keep `proxy_ssl_server_name on` and set `proxy_ssl_name $gateway_host` if needed for SNI when the URL is https; do not set `Origin` (pass the browser's through untouched); keep `X-Forwarded-For`/`X-Forwarded-Proto` handling but use `$http_x_forwarded_proto` when present (Cloud Run terminates TLS in front of nginx so `$scheme` is always `http` inside the container).
- Keep every existing security header in each location (the `add_header` inheritance rule) and all current behaviour (`proxy_buffering off`, `proxy_read_timeout 3600s`...). Add a `location = /healthz { return 200 'ok'; }` WITHOUT the CSP header being required there but with `access_log off`.
