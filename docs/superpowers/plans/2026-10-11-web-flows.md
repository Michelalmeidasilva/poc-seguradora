# Web Flows Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the `FlowPlaceholder` with a real WhatsApp Flows engine in `apps/web/src/flows`: it opens a `message.flow` as a bottom sheet, renders every component of spec section 5, runs the expression language and the actions, and sends `user.flow_submit` / `user.flow_data_exchange`.

**Architecture:** Feature slice `flows/` with a framework-free core (`schema`, `expr`, `runtime`) and a React layer (`components/` registry, `FlowSheet`). The runtime is a pure reducer over `{ stack, data, form, errors }`; components render from it and dispatch actions. The chat only knows `OpenFlow` (`renderers/flow-host.ts`) and `useChat.sendFlowSubmit`/`sendFlowDataExchange`.

**Tech Stack:** React 19.3, TS strict (`noUncheckedIndexedAccess`), Zod (already in the monorepo), Vitest + Testing Library, Playwright (local e2e). No new runtime dependency. No `eval`/`Function`: expressions have their own parser.

**Spec:** `docs/superpowers/specs/2026-10-10-whatsapp-chatbot-poc-design.md` (section 5 for the engine, 4 for the sheet UX, 14 for code rules); contract in `docs/superpowers/specs/2026-10-10-gateway-chatbot-contract.md`.

## Global Constraints

- Flow JSON is untrusted input (it comes from the server): never `eval`, never `dangerouslySetInnerHTML`, URLs only through `renderers/safe-urls` (`http(s)` for `open_url`/`EmbeddedLink`/`Image src`; `data:image/` allowed only for `Image`/`ImageCarousel`).
- Limits from the spec: 50 components per screen; Footer max 1 per screen; EmbeddedLink max 2; Image max 3; OptIn max 5; CheckboxGroup 1–20 options; Dropdown 1–200; TextHeading/TextSubheading 80 chars; TextCaption 409; TextBody 4096; `If` nesting max 3; `routing_model` max 10 branches per screen; screen id `SUCCESS` is reserved. Over-limit JSON is **rejected whole** with a friendly message, never half-rendered.
- NavigationList, ChipsSelector and ImageCarousel are not officially documented: implement only what spec section 5 confirms; every other choice (item limits: NavigationList 20, ChipsSelector 20 options, ImageCarousel 10 images) is recorded in the ledger as a `Ruling:` and in `CHECKLIST.md` under "Decisões próprias".
- Footer is blocked while any visible field is invalid. Fields hidden by `visible: false`/`If`/`Switch` are neither validated nor submitted.
- Sensitive data: `flow_submit.data` is **not** persisted in `sessionStorage`; only the `summary` text is (decision for the open item of Plan 4). Screens/fields with `sensitive: true` are masked (`••••`) in the summary.
- Dependency rules (depcruise): `flows/expr`, `flows/schema`, `flows/runtime` import no React and nothing outside `flows/`; `flows/` imports nothing from `chat/` or `transport/`; `flows/` may import `ui/` and `renderers/safe-urls`; `chat/` and `app/` reach `flows/` only through its `index.ts`.
- Ownership: this plan edits `apps/web/src/flows/**` (row `web-flows`) and, for integration only, `apps/web/src/app/App.tsx`, `apps/web/src/renderers/flow-host.ts`, `apps/web/src/chat/useChat.ts` (one new method), `apps/web/src/transport/chat-client.ts` (one new `Draft` variant), `eslint.config.js`, `.dependency-cruiser.cjs`, `apps/web/CHECKLIST.md`. The `web-chat` row is `done`; record the integration touch in the `web-flows` row `Notas`.
- Code language English, UI strings pt-BR, commits conventional, `CHECKLIST.md` item ticked in the same commit as its code.

## Review Focus

1. A Flow with a screen that references `${form.x}` of a field on a previous screen (not allowed by Meta): expect a validation error at open, not `undefined` rendered.
2. User goes Back and forward: form values of earlier screens are kept; `data` of a screen is the `navigate` payload of the **last** navigation into it.
3. Double-click on Footer (`complete`): exactly one `user.flow_submit`.
4. `${data.missing}` / `${form.empty}` in a payload: resolves to `""`/`null` per field type, never the literal `"undefined"`.
5. Escape and the Close button with unsaved input: asks for confirmation (`Descartar o formulário?`) instead of silently losing input.
6. A Flow JSON that is huge, deeply nested or cyclic in `routing_model`: rejected quickly (bounded work), UI stays responsive.

### Task 2: Expression engine

**Files:**
- Create: `apps/web/src/flows/expr.ts`, `apps/web/src/flows/expr.test.ts`

**Interfaces:**
- Produces:
  - `type Scope = { data: Record<string, unknown>; form: Record<string, unknown> }`
  - `interpolate(template: string, scope: Scope): string` — replaces each `${data.a.b}` / `${form.x}` inside a string; missing → `""`.
  - `resolveValue(value: unknown, scope: Scope): unknown` — if `value` is exactly one `${...}` returns the raw typed value (number, boolean, array, `null` when missing); otherwise `interpolate`. Objects/arrays are resolved recursively (used for action payloads).
  - `evalCondition(source: string, scope: Scope): Result<boolean, string>` — grammar below. Non-boolean result → `err('not_boolean')`.
  - `hasDynamicValue(source: string): boolean` (used by Task 1 validation: import it there, so Task 1 stubs it as `/\$\{(data|form)\./.test(src)` and Task 2 replaces the stub with the import).

Grammar for conditions (precedence low→high): `||`, `&&`, `== !=`, `> >= < <=`, unary `!`, primary (`${ref}`, string literal `'..'` or `".."`, number, `true`, `false`, `null`, `( expr )`). Reject: any other character, depth > 20, source > 500 chars. Comparison across types (`'1' == 1`) is false for `==` and true for `!=`; `>`/`<` on non-numbers → `err('type_mismatch')`.

- [ ] **Step 1: Tests first.** Table-driven: every operator with true/false cases, parentheses and precedence (`a || b && c`), `!` on a missing reference (missing is `null`; `!null` → true), strings with `&&` inside quotes, `${data.a.b}` nested path, array index is **not** supported (`${data.a[0]}` → `err`), injection attempts (`constructor`, `__proto__`, `toString` as path segments resolve to `null`: use `Object.hasOwn` at each step), 501-char source, 25 nested parentheses, `1 +` (syntax error → `err`, never throws), `resolveValue` keeps types (`"${form.n}"` with `n = 3` → `3`), mixed text `"Olá ${form.n}!"` → string.
- [ ] **Step 2:** Run → FAIL.
- [ ] **Step 3: Implement** a tokenizer + recursive-descent parser + evaluator. No `RegExp` with nested quantifiers. Every public function is total (returns, never throws).
- [ ] **Step 4:** PASS + typecheck + lint + depcruise.
- [ ] **Step 5:** Tick "Motor de expressões"; commit `feat(web): flow expression engine`.

### Task 3: Runtime (state machine and validation)

**Files:**
- Create: `apps/web/src/flows/runtime.ts`, `apps/web/src/flows/runtime.test.ts`, `apps/web/src/flows/validation.ts`, `apps/web/src/flows/validation.test.ts`

**Interfaces:**
- Consumes: `FlowJson`, `FlowScreen`, `FlowComponent`, `FlowAction` (Task 1); `Scope`, `resolveValue`, `evalCondition` (Task 2).
- Produces:
  ```ts
  export interface RuntimeState {
    stack: { screenId: string; data: Record<string, unknown> }[]; // last = current
    form: Record<string, unknown>;       // all fields by name, across screens
    touched: Record<string, true>;
    pending: 'idle' | 'exchange';        // data_exchange in flight
    outcome?: { kind: 'complete'; payload: Record<string, unknown> };
  }
  export type RuntimeEvent =
    | { type: 'set'; name: string; value: unknown }
    | { type: 'touch'; name: string }
    | { type: 'back' }
    | { type: 'navigate'; screenId: string; payload: Record<string, unknown> }
    | { type: 'complete'; payload: Record<string, unknown> }
    | { type: 'exchange_start' } | { type: 'exchange_done' }
    | { type: 'update_data'; patch: Record<string, unknown> };
  export function initRuntime(flow: FlowJson): RuntimeState;
  export function reduce(flow: FlowJson, s: RuntimeState, e: RuntimeEvent): RuntimeState;
  export function currentScreen(flow: FlowJson, s: RuntimeState): FlowScreen;
  export function scopeOf(s: RuntimeState): Scope;
  export function visibleComponents(screen: FlowScreen, scope: Scope): FlowComponent[]; // flattens If/Switch, drops visible:false
  export function validateField(c: FlowComponent, value: unknown): string | undefined; // pt-BR message
  export function screenErrors(flow, s): Record<string, string>; // visible fields only
  export function footerDisabled(flow, s): boolean;
  ```
- Rules: `navigate` pushes `{screenId, data: payload}` (replacing `data` if the screen is already on the stack top is a no-op); `back` pops (never below entry); `complete` is ignored if `outcome` is already set (double-click); `set` for a name never on the current visible set is ignored. `validateField`: `required`, `min-chars`/`max-chars`, `input-type` (`number`, `email`, `phone`, `password`, `passcode`, `text`), `pattern` is **not** supported (not in spec), `error-message` property overrides the default text, `helper-text` is display only; CheckboxGroup `min-selected-items`/`max-selected-items`; DatePicker `min-date`/`max-date`; OptIn `required` means must be checked; PhotoPicker/DocumentPicker `min-uploaded-*`.

- [ ] **Step 1: Tests first** covering: init at entry screen; navigate/back keeps `form` but replaces nothing else; duplicate `complete` ignored; `${form.x}` resolved in navigate payloads (use cotacao fixture: PRODUTO → DADOS carries `produto`); Switch on `${data.produto}` shows only the AUTO branch fields; hidden branch fields are not in `screenErrors` and not in the complete payload (Review Focus 4); `footerDisabled` true until required fields valid; each `validateField` rule with a valid and an invalid value; `error-message` override.
