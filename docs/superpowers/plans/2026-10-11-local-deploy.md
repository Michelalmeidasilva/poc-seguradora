# Local Per-Service Deploy Implementation Plan (Plan 8)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the GitHub-Actions deploy (Plan 7) by a local, CLI-driven deploy where **each service can be deployed on its own** (`web`, `gateway`, `chatbot`, `svc-cotacao`, `svc-apolice`, `svc-sinistro`), configured entirely through a git-ignored `infra/.env`, plus a project **skill** that tells an agent how to run the script with the right flags per service.

**Architecture:** Terraform owns the *shape* of the platform (APIs, registry, VPC, service accounts, secret, six Cloud Run services with their env, scaling, ingress, IAM, budget) but **not the container image** of any service: each Cloud Run service is created with a public placeholder image and `lifecycle.ignore_changes` on the image. `infra/deploy.sh` owns the *image* of each service: `build` (docker buildx → Artifact Registry) and `deploy <service>` (`gcloud run services update <service> --image …`), so deploying `gateway` never touches `web` or the Terraform state, and rollback is "update the image back to a previous tag". Infrastructure/config changes go through `deploy.sh infra plan|apply`. The script is bash 3.2-compatible and testable offline with fake `gcloud`/`docker`/`terraform` binaries on `PATH`.

**Tech Stack:** bash 3.2, gcloud, docker buildx, Terraform ≥ 1.10, Node 22 (smoke). No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-10-whatsapp-chatbot-poc-design.md` section 12; supersedes the GitHub-Actions part of `docs/superpowers/plans/2026-10-11-deploy-ready.md` (Plan 7). Dockerfiles, compose, smoke, nginx hardening, runbook structure, Terraform network/secret/budget stay.

## Global Constraints

- **Nothing in this plan calls GCP.** No real `gcloud`, `terraform plan/apply`, docker push. The script is exercised only against fake binaries; Terraform is verified with `fmt`, `init -backend=false`, `validate`.
- **Services and the registry of them live in ONE table inside `deploy.sh`** (name → Dockerfile → build context → Cloud Run service name): `web` → `apps/web/Dockerfile`; `gateway` → `apps/gateway/Dockerfile`; `chatbot` → `apps/chatbot/Dockerfile`; `svc-cotacao` → `apps/svc-cotacao/Dockerfile`; `svc-apolice` → `apps/svc-apolice/Dockerfile`; `svc-sinistro` → `apps/svc-sinistro/Dockerfile`. All build contexts are the repo root; every image listens on `8080` and answers `GET /health` (documented convention for the `svc-*` owner; recorded in the `deploy` row Notas, not in their paths). **Fallback while a `svc-*` has no Dockerfile** (the real services are another agent's work): `build svc-X` uses `infra/fake-services/Dockerfile` (the contract-conformant fake serves all three contracts) and prints a loud `AVISO: imagem FAKE` line, tagging it `svc-X:<tag>` like any other image, so each of the three Cloud Run services stays independently deployable and the real image replaces it simply by adding `apps/svc-X/Dockerfile`.
- **Configuration only through `infra/.env`** (git-ignored; `infra/.env.example` committed with every key documented, no secrets): `PROJECT_ID`, `REGION` (default `southamerica-east1`), `TF_STATE_BUCKET`, `ARTIFACT_REGISTRY_REPO` (default `seguradora`), `LOG_LEVEL`, `TRUST_PROXY_HOPS` (default 3), `WEB_CUSTOM_DOMAIN_URL`, `BILLING_ACCOUNT_ID`, `BUDGET_AMOUNT_BRL`, `BUDGET_ALERT_EMAIL`, and per-service scaling `<SVC>_MIN_INSTANCES` / `<SVC>_MAX_INSTANCES` / `<SVC>_MEMORY` with `SVC` ∈ `WEB GATEWAY CHATBOT SVC_COTACAO SVC_APOLICE SVC_SINISTRO` (defaults: min 0; max 2 for web and 1 for all others — their state is in memory; memory 256Mi web, 512Mi others). `--env-file <path>` overrides the default. The script maps them to `TF_VAR_*`; Terraform variables stay the source of truth for defaults.
- **Safety defaults:** every mutating command prints what it will do and asks for a typed confirmation unless `--yes`; `destroy` always requires `--confirm-project <id>` AND the id typed; `build`/`deploy` refuse a dirty git tree unless `--allow-dirty`; `build` refuses to overwrite a tag that already exists in the registry; `deploy --existing-tag` and `rollback` verify the image exists at the tag first; `terraform apply` always applies a saved plan, the plan file lives in a private temp dir (`mktemp -d`, mode 700, outside the repo, removed on success, failure and Ctrl-C) because it holds the session secret in plaintext.
- **Auth model:** the operator's own identity (`gcloud auth login` + `gcloud auth application-default login`); no service-account keys, no WIF, no GitHub involvement. The runbook lists the minimal roles.
- **Terraform after the change keeps:** APIs, Artifact Registry (+cleanup policy), VPC/subnet, runtime service accounts (one per service), Secret Manager secret + accessor for the gateway SA, **six** Cloud Run services (`web` and `gateway` public; `chatbot`, `svc-cotacao`, `svc-apolice`, `svc-sinistro` with internal ingress and Direct VPC egress where they call others) with `allUsers` invokers (Plan 7 ruling stays), optional budget. **Removed:** the `deployer` SA + its roles + `actAs` bindings, WIF pool/provider/bindings, `github_repository`, `github_deploy_branch`, the single `fake_services` service, the variables `deploy_fake_services` and `service_urls`, `image_tag`, and the outputs `deployer_service_account`/`wif_provider`; APIs only those needed are dropped. Each service: placeholder image `us-docker.pkg.dev/cloudrun/container/hello`, TCP startup probe on 8080 (the placeholder has no `/health`; the HTTP `/health` probes of Plan 7 move to a pendência), `lifecycle { ignore_changes = [template[0].containers[0].image] }` (also ignore the client/client_version metadata `gcloud` rewrites, to keep `plan` clean after a `gcloud` deploy). Chatbot env `COTACAO_URL/APOLICE_URL/SINISTRO_URL` point at the respective `svc-*` URL. Per-service scaling comes from one `service_scaling` map variable.
- Bash must run on macOS bash 3.2 (no empty-array expansion under `set -u`, no `mapfile`, no associative arrays, no `${var,,}`), `set -euo pipefail`, quote everything, no `eval`, no secrets echoed.
- **Skill:** `.claude/skills/deploy-service/SKILL.md` (project skill, like `workboard-protocol`). Frontmatter `name` + `description`; body in pt-BR: when to use; mandatory first step `bash infra/deploy.sh check`; mapping from natural requests to commands per service; flags reference; hard rules for the agent (never pass `--yes`/`--confirm-project` unless the user explicitly said so in the current request; never run `destroy` on its own initiative; always show the user the plan output before asking for confirmation; never print or store secrets; stop and report on any non-zero exit with the exit-code meaning; `svc-*` without a Dockerfile deploys the FAKE image and the agent must say so; do not edit `apps/svc-*`). A checker verifies that every service and flag in the skill exists in `deploy.sh help` and vice versa. `AGENTS.md` gets one line pointing agents of other tools to the same script and rules.
- Conventional commits; comments English, docs pt-BR; `CHECKLIST.md`/`WORKBOARD.md` honest (row `deploy` reopened).

## Review Focus

1. Deploying one service must not touch another: the logged `gcloud`/`terraform` calls for `deploy gateway` mention only the gateway service; `terraform` is not invoked at all by `deploy <service>`.
2. A mistyped/missing confirmation never mutates: any answer other than the exact expected string aborts (exit 4) with no mutating command in the fake-binary log. `destroy` impossible by accident.
3. `deploy all` order (leaf services first): `svc-cotacao`, `svc-apolice`, `svc-sinistro`, `chatbot`, `gateway`, `web`; the smoke runs once at the end; a failed deploy of one service stops the rest and says which were already updated.
4. Terraform `plan` after `gcloud services update --image` must show no image diff (ignore_changes) — documented, and asserted structurally in `validate.sh`.
5. First deploy works with no images yet (placeholder image) — no chicken-and-egg: `bootstrap` → `infra apply` → `deploy all`.
6. Removing WIF/deployer/GitHub deploy leaves no dangling references anywhere (Terraform, validate.sh, README, runbook, checkers, ignore files, CI lint scripts).
7. The skill cannot drift from the CLI (checker) and cannot talk an agent into destructive actions (rules are explicit and checked by the checker: the skill text must contain the prohibitions).
